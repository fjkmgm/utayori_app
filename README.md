## 1. サービス概要
- **サービス名（仮）**：UTAYORI（うたより）- 一日の終わりに、百人一首が寄り添う処方箋日記
- **どんなサービスか**：一日の終わりの感情や短い出来事を書くと、その心情に重なる百人一首が提案され、千年前の歌人と感情を共有しながら静かに心を整えられる日記サービス。
- **誰の、どんな課題を、どう解決するか**：夜ベッドの中で「一人反省会」をしてしまう人が、SNSに吐き出せない日常のモヤモヤを古典の言葉と重ね合わせることで、風情ある余韻へと昇華して心地よく一日を終えられるようにする。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情
私自身、現在仕事と育児の両立に追われる子育てワーママです。朝から晩まで仕事・家事・育児に追われ、夜子どもを寝かしつけた後のベッドの中で「今日も子どもに怒りすぎてしまった」「仕事も中途半端だったな」と一人反省会をしてしまう毎日を過ごしています。
家族やママ友には気を遣って言えず、SNSに愚痴を書くのも憚られるため、気づけばスマホでAI（ChatGPT等）に向かってその日のモヤモヤを吐き出していました。
そんなとき、ふと昔少し競技かるたをやっていたこともあり、「百人一首」の歌を思い出す瞬間がありました。「千年前の人たちも、現代の私たちと全く同じように思い通りにいかない日々に心を揺らし、言葉に昇華していたんだ」と気づき、ささくれ立っていた気持ちがふっと軽くなった経験が原点です。

### 2-2. なぜそれが「気になった」のか
自分が情緒や言葉の響きを大切にしたいタイプであること、そしてかるたを通して三十一文字の背景にある人間のリアルな感情を知っていたからです。
同じように忙しくても割り切れる人はいますが、私は「日々の小さな苛立ちやモヤモヤを抱え込んだまま眠りにつくこと」に小さな苦しさを感じていました。機械的な解決策ではなく、古典の言葉を借りることで、日々の疲労や自己嫌悪を豊かな「余韻」に変えたいと考えました。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと
日々の仕事と育児の疲れやモヤモヤを吐き出す場所がなく、夜ひとりでスマホに向かって愚痴を吐き出し、余計に自己嫌悪に陥ってしまうこと。

### 3-2. 本当に解決したい課題は何か
- **なぜ？**：家族や友人には気を遣って本音の愚痴が言えず、一人で抱え込んでしまうから。
- **なぜ？**：AIに愚痴を吐き出しても、合理的なアドバイスや正論が返ってきてしまい、「アドバイスではなく感情を受け止めてほしい」という気持ちが満たされないから。
- **なぜ？**：自分の感情を穏やかに受け止め、肯定してくれる安全な居場所がないから。
- **→ 本当に解決したい課題**：
  仕事と育児に追われる中で自分の感情を味わう余裕を失い、日々の葛藤や疲労を「自己嫌悪」として消費したまま、トゲトゲした心で一日を終えてしまうこと。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー
- **年齢設定**：
  - **年齢**：30代女性（32〜38歳程度）
  - **理由**：仕事での責任と未就学児〜低学年の育児が重なり、もっとも自分の時間や心の余裕を失いやすい世代だから。
- **生活・状況設定**：
  - **生活・状況**：時短またはフルタイムで働きながら未就学児を育てるワーキングマザー。朝夕の送迎・仕事・夕飯・お風呂・寝かしつけまで息をつく暇がなく、夜ベッドに入った瞬間だけが唯一の自分時間。
  - **理由**：就寝前のわずか3分、片手入力の短文だけで完結し、張り詰めた神経を静かに緩める体験がもっとも切実に求められる環境だから。
- **環境設定**：
  - **環境**：リアルな知人（夫・ママ友・同僚）には愚痴や弱音を吐き出せず、日常的にAIチャットやスマホの非公開メモ帳にモヤモヤを書き込んでいる環境。
  - **理由**：人に直接見せる場所ではない「自分と古典だけの静かな対話空間」として提供することで、安心して感情を吐き出せる。

### 4-2. 自分とユーザーの距離
- **自分自身**
- **理由**：まさに現在、仕事と育児を両立する中で夜ベッドに入ってAIに愚痴を打ち込んでいる自分自身の切実な実体験に基づいているため。

### 4-3. 実際に使われる可能性について(需要・存在確認)
- **まず最初に使ってくれそうな人**：自分自身、および読書や言葉が好きで夜に考え事をしてしまいがちな身近な友人。
- **どんな場面で思い出すか**：夜、お風呂から上がってベッドに入り、照明を落として「今日一日が終わるな」と息をついた瞬間。
- **代わりに使っているもの**：スマートフォンの標準メモ帳、Xの鍵アカウント、手書きの簡易日記帳。
- **置き換えてまで使う理由**：単に記録するだけでなく、「あなたのその気持ち、千年前のこの歌と同じですよ」と百人一首が寄り添ってくれる体験（自己受容と情緒ある現代語訳の提示）が得られるから。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)
- **きっかけ**：SNSやWeb検索で「一人反省会を止める方法」「百人一首で心を整える日記」として知る。
- **最初の一歩**：会員登録後、まずは今の気分を一言（例：「今日も頑張ったのに空回りして疲れた」「秋風が冷たくて少し寂しい」）入力して投稿ボタンを押すだけ。
- **利用を続ける理由**：
  - 短文で済むため記録のハードルが極めて低いこと。
  - カレンダーに「今日の一首」が積み重なり、自分の感情のログが雅な歌集のようにコレクションされていく達成感があること。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

### 5-2. それでも自分が作りたい理由
AIに愚痴を打つと「それは大変ですね。解決のためにご主人とルールを決めましょう」「明日はこう工夫しましょう」といった正論のアドバイスが返ってくることが多く、疲れている夜にはその正論すら重荷に感じることがありました。
ワーママが夜に求めているのは「解決策や分析」ではなく、「ただその感情の存在を許され、美しいものとして昇華されること」です。千年の時を超えて残ってきた百人一首の言葉だからこそ、説教くさくならずに深い安らぎを与えられると考えました。

### 5-3. 差別化を「体験価値」で表現する
- **私のアプリの差別化ポイント**：

## 7. このアプリで実現すること

### MVPで作る機能
1. **ユーザー認証機能**
   - ユーザー登録・ログイン・ログアウト（メール/パスワード または Sorcery）
2. **日記投稿・キーワードマッチング機能（サービスの核）**
   - 日記入力（タイトル・本文テキスト）
   - 本文内のキーワード（「秋」「雨」「疲れた」「寂しい」「会いたい」など）を抽出し、事前登録された百人一首データベースから最適な1首を提案・自動紐付け
   - 紐付いた歌の「上の句・下の句」「現代語訳」「歌人の背景・解説」を表示
3. **日記閲覧・管理機能**
   - 自分の投稿一覧表示（今日の一言 ＋ 提案された歌）
   - 日記の詳細表示・編集・削除
4. **百人一首の一覧・詳細検索**
   - 収録されている歌と現代語訳を閲覧できる機能

### 本リリースで作る機能
1. **カレンダービュー機能**
   - 日記を書いた日に札のアイコンが並び、自分だけの「歌集」が完成していくUI
2. **お気に入り・振り返り機能**
   - 心に響いた歌のクリップ機能、過去の同じ感情の日の振り返り
3. **X（旧Twitter）シェア機能**
   - 「今日の一首」をカード画像（OGP）としてSNSに美しく共有
4. **感情タグの複合判定**
   - キーワードだけでなく、「恋」「哀傷」「四季」「雑」などの感情カテゴリ選択を組み合わせた高精度な提案

## 8. このアプリの懸念点とその対策

### 懸念点①
- **何が問題になりそうか**：ユーザーが入力した文章にキーワードが含まれず、歌がマッチングしないケースが発生すること。
- **なぜそう思うか**：自由記述のテキストから完全一致のみで判定すると、言葉のブレ（「疲れた」と「しんどい」など）に対応しきれない可能性があるため。
- **そのために考えている対策**：
  - 代表的な感情キーワードの類語辞書をシードデータ側で簡易定義しておく。
  - キーワードが見つからなかった場合は、フォールバックとして「今日の日付（季節）」に合った歌を提案し、マッチング失敗による体験の途切れを防ぐ。

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術
- **バックエンド**：Ruby 3.2系 / Ruby on Rails 7系
- **フロントエンド**：Rails標準（Hotwire: Turbo / Stimulus）、Tailwind CSS / daisyUI
- **データベース**：PostgreSQL
- **デプロイ先**：Render（Web Service / PostgreSQL）
- **主要Gem**：sorcery（認証）、meta-tags（OGP）、kaminari（ページネーション）

### 10-2. 技術選定の比較検討

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Rails + Hotwire (Turbo/Stimulus) | 採用 | MVP開発におけるスピードを最優先し、単一フレームワークでリッチなUIと高い生産性を両立できるため。 |
| Next.js / React (SPA構成) | 不採用 | 画面遷移や状態管理の学習コストが高く、MVPの検証および納期を圧迫するリスクがあるため。本リリース以降に検討。 |
| Render | 採用 | Rails + PostgreSQL環境を低コストかつ迅速にデプロイでき、個人開発の運用負担が少ないため。 |
| AWS (EC2/RDS) | 不採用 | インフラ構築の学習は完了しているが、初期リリース段階での運用・コスト面を考慮しマネージドサービスを優先。 |

- **今回チャレンジしたい点**：Tailwind CSS / daisyUI を用いた、夜の利用に適した静謐で洗練された和風モダンUIのデザイン実装。
- **不安な点**：キーワードマッチングの精度調整と、百人一首データ（歌・現代語訳・キーワード）のシードデータの作成量。

### 10-3. キャッチアップ不足の懸念
SPA（React等）の導入はMVP時点では見送り、Rails標準の機能（Hotwire等）に集中することで見積もりのブレを防ぎます。百人一首のデータ整備については、最初から100首すべてに細かなキーワードを設定するのではなく、MVP時点では代表的な30〜40首に絞ってマッチング精度を担保する方針を取ります。
